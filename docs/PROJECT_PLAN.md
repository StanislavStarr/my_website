# Лендинг Станислава Синицына: план, позиционирование и дизайн

## Цель и границы первого этапа

Спроектировать личный сайт, который приводит обращения по веб- и мобильной разработке. Посетитель должен быстро понять, какие задачи решает Станислав, увидеть подходящий опыт и отправить описание своего проекта.

Структура, композиция и визуальный стиль прототипа утверждены пользователем. Сохраняем их при дальнейшей реализации. Текущий этап: перенос утверждённого дизайна в Next.js и подготовка исходников для локального запуска; публикация ещё не выполнялась.

Исходные данные: актуальный файл «Станислав Синицын CV.pdf», добавленный 31 октября 2026; пожелания из текущего запроса; ранее выбранные пользователем ориентиры kiendt.dev и kane.ink. Факты из резюме отражают заявленный профессиональный опыт, а не независимый аудит результатов.

## Рабочая гипотеза позиционирования

Наиболее убедительное направление по резюме — разработка и развитие B2B-продуктов: SaaS, CRM, личные кабинеты, сервисы с интеграциями и сложными пользовательскими сценариями. В эту же историю вписываются MVP для стартапов. Пользователь подтвердил, что берёт в работу отдельные доработки. Стоимость обсуждается на личной встрече; публичный прайс и минимальный бюджет на лендинг не выносим.

Подтверждённые услуги: веб-разработка, приложения для iOS/Android, PWA и Telegram Mini Apps. Подтверждены технологии личного исполнения: iOS/Android — React Native + Expo; PWA и Telegram Mini Apps — React/Vue. Новые мобильные кейсы для старта не требуются. Каналы обращения: Telegram и email. Пользователь разрешил использовать названия, скриншоты и ссылки на проекты; сами материалы нужно собрать.

Формат бренда — личное имя и личная ответственность за проект. Подтверждено самостоятельное исполнение с возможностью привлечения команды под объём и специализацию задачи. Основной голос сайта — «я». Английская формулировка: “I work directly with you and bring in specialists when the project needs them.” Постоянный штат и агентство не заявляем.

Языки утверждены: английский — основной, русский — дополнительный. География подтверждена: международные клиенты из разных стран, без ограничения одним национальным рынком. Рабочая гипотеза сегмента — компании и основатели цифровых продуктов, включая B2B SaaS, CRM и MVP. Язык посетителя не приравниваем к его стране.

GEO в этом плане означает Generative Engine Optimization: работу над обнаружением, пониманием и цитированием сайта в ИИ-поиске. Географию продаж определяем отдельно.

### eKhonish — MVP и развитие платформы

Публичная ссылка, переданная пользователем: https://ekhonish.tj/. Сайт описывает цифровую образовательную экосистему. Текущие цифры пользователей, отзывы и изображённые интерфейсы не становятся личными достижениями Станислава автоматически. Кейс описывает работу из резюме, а ссылка ведёт к продукту.

Руководил командой разработки и QA, вместе с заказчиком определял требования и приоритеты. Команда выпустила MVP в согласованные сроки. Унифицировал аутентификацию между приложениями и сократил объём frontend-бандла примерно на 30%.

Для полной версии: показать интерфейс, уточнить состав продукта и границы собственной ответственности. В резюме также указаны UI Kit из 25+ компонентов и ускорение разработки повторяющихся интерфейсов примерно на 25%; для публичного кейса нужно описать способ оценки и сопоставляемые задачи. Привлечение инвестиций после MVP не представлять как результат исключительно frontend-работы.

### РЖД — личный кабинет грузоперевозок

Публичная ссылка, переданная пользователем: https://cargolk.rzd.ru/. Название РЖД теперь подтверждено самим пользователем. Прямое чтение страницы 3 ноября 2026 завершилось тайм-аутом; скриншоты интерфейса не получены.

Разработал ключевой сервис создания и бронирования перевозок, дашборды, отчётность и отслеживание на карте. Провёл миграцию Vue без остановки разработки новых функций. После перехода с Webpack на Vite локальный запуск сократился примерно с трёх минут до 30 секунд.

Для клиента на первом плане — возможности продукта и продолжение выпуска функций во время модернизации. Ускорение запуска относится к работе команды разработчиков, а не к загрузке сайта посетителем. Оценку влияния на прибыльность из резюме не выносить в главный тезис без контекста методики. Указывать роль в команде, не обозначать весь продукт как самостоятельно разработанный.

### Client Base — CRM и электронный документооборот

Развивал CRM-конструктор, интерфейсы управления клиентами и заказами, отчёты и дашборды. Интегрировал подписание документов через SignNow и синхронизацию изменений через webhooks. Выполнял полный цикл разработки функций: от моделей данных и API до пользовательского интерфейса.

Для полной версии: выбрать один сквозной сценарий, например подготовку и подписание документа, и показать его на нескольких экранах. Денежный эффект и экономию времени добавлять только при наличии данных.

### MedTech — работа с оборудованием клиники

Разработал интерфейсы санитарного цикла оборудования примерно из 11 этапов с обработкой неисправностей и нарушений стерильности. Реализовал сценарии сканирования штрихкодов, печать этикеток и доступ по ролям. Адаптировал интерфейсы под сканеры и клинические рабочие станции.

Для полной версии: объяснить сценарий простыми словами, уточнить допустимое название продукта и подготовить обезличенные изображения. Не приписывать интерфейсу клинические результаты, которых нет в исходных данных.

На лендинге утверждены четыре кейса: eKhonish, РЖД, Client Base и MedTech. MedTech добавлен в прототип на английском и русском, без изменения оформления остальных блоков. Мобильная разработка подтверждена как предлагаемая услуга; мобильный кейс в прочитанном резюме не указан. Отсутствие нового материала не блокирует первую версию, но конкретную мобильную технологию и формат исполнения нужно корректно описать.

Игра и анимации интерфейса подчиняются общему ритму: дискретное ретро-движение внутри игрового экрана, мягкие современные переходы вокруг него. Постоянное движение ограничиваем одной второстепенной текстовой строкой; её можно остановить. При prefers-reduced-motion непрерывное движение и магнитные смещения отключаем. Обычную прокрутку страницы сохраняем.

## Языковые версии

Пользователь предлагает i18n. Используем этот подход к локализации: общие компоненты, словари интерфейса и отдельный контент кейсов. Конкретная библиотека зависит от выбранного фреймворка; она пока не утверждена. Для поисковой индексации производственная версия должна отдавать отдельный HTML каждой локали через SSR/SSG. Переключение словаря на одном URL в дизайн-прототипе служит только демонстрацией.

Английская версия основная. Предлагаемая структура URL: `/` для английской главной и `/ru/` для русской. У отдельных кейсов и услуг будут соответствующие пары адресов.

- Переключатель EN / RU в навигации; выбор посетителя сохраняется.
- Переход между языками ведёт к соответствующей странице, когда перевод существует.
- Отдельные заголовки страниц, описания, контент и корректный lang для каждого языка.
- Для каждой страницы — собственный canonical, взаимные hreflang en/ru; x-default указывает на английский адрес.
- Первое открытие по умолчанию на английском; автоматический обязательный редирект по IP не нужен.
- SEO-семантика и формулировки услуг готовятся для каждого языка отдельно. Английский язык сам по себе не определяет страну продаж.
- Состав услуг, кейсов и контактные данные согласованы между переводами.

Основание для структуры языковых версий: [документация Google](https://developers.google.com/search/docs/specialty/international/managing-multi-regional-sites) и [hreflang](https://developers.google.com/search/docs/specialty/international/localized-versions).

## План SEO и GEO

### Сначала — семантика и содержание

Для международной английской версии и дополнительной русской собрать коммерческие запросы и разнести их по задачам: создание веб-приложений, SaaS/MVP, CRM и кабинеты, модернизация, мобильная разработка. Это кандидаты на группы запросов, а не уже проверенная частотность. Точные формулировки и конкуренция зависят от языка и региона.

Главная остаётся лендингом. Для развития органического поиска предлагается предусмотреть самостоятельные страницы нескольких приоритетных услуг и кейсов. Отдельная страница нужна там, где есть самостоятельный запрос и полезное содержание; создавать множество однотипных страниц под каждую вариацию запроса не нужно.

### Техническая база

- Основной контент доступен в первоначальном HTML; выбрать статическую генерацию или серверный рендеринг по задачам проекта.
- Уникальные заголовки и описания страниц, логичная иерархия заголовков, понятные ссылки.
- Корректные canonical, sitemap, robots.txt и HTTP-статусы.
- Две языковые версии: английская основная, русская дополнительная; отдельные URL, ручное переключение и корректные hreflang. [Документация Google](https://developers.google.com/search/docs/specialty/international/managing-multi-regional-sites).
- Оптимизированные изображения, доступность и проверка скорости на мобильных устройствах.
- Структурированные данные только о реально представленной информации; разметка соответствует видимому тексту.
- Подключение Search Console, других кабинетов поиска и аналитики по выбранным рынкам.

### Содержание для ИИ-поиска

Понятно описать специализацию, автора, услуги и роль в каждом кейсе. Дать конкретные ответы на вопросы потенциальных клиентов, добавить реальные подтверждения и актуальные сведения. Проверить, что нужным поисковым роботам не мешают robots.txt и правила хостинга.

Google указывает, что для AI Overviews и AI Mode сохраняются основные принципы SEO; специальная AI-разметка и отдельные AI-текстовые файлы не требуются. Выполнение требований не гарантирует индексацию или показ. [Источник](https://developers.google.com/search/docs/appearance/ai-features).

Для поиска ChatGPT проверяется доступ OAI-SearchBot; это отдельная настройка от GPTBot, связанного с обучением моделей. [Документация OpenAI](https://developers.openai.com/api/docs/bots).

Результаты измеряем через обнаруженные переходы, обращения и периодические проверки видимости по заранее выбранным запросам. Единичный ответ ИИ не считать постоянной позицией. Переходы из Google AI-функций входят в общую поисковую статистику Search Console, поэтому полная отдельная атрибуция GEO может быть недоступна.

## Международное SEO и GEO: стратегия первой версии

Стартуем с одного международного сайта на нейтральном домене, например .com, если подходящее имя доступно. Английская версия предназначена для клиентов из разных стран, русская — для русскоговорящих клиентов независимо от места проживания. Не создаём одинаковые посадочные страницы для десятков стран.

| Версия | Адреса | Сигнал языка |
| --- | --- | --- |
| Основная английская | `/`, `/work/medtech/` и другие кейсы | `en` |
| Русская | `/ru/`, `/ru/work/medtech/` и соответствующие кейсы | `ru` |
| Версия по умолчанию | Соответствующая английская страница | `x-default` |

У каждой страницы собственный canonical; переводы связываются взаимными hreflang и доступны через обычные ссылки. В sitemap включаем реальные индексируемые страницы. Автоматические перенаправления по IP не используем. Язык в URL сохраняет приоритет; языковой переключатель ведёт к тому же кейсу на другом языке. Основание: [Google — многоязычные сайты](https://developers.google.com/search/docs/specialty/international/managing-multi-regional-sites) и [локализованные версии](https://developers.google.com/search/docs/specialty/international/localized-versions).

Первые поисковые гипотезы строим вокруг задачи и специализации: SaaS/MVP, личные кабинеты, CRM, модернизация, PWA и Telegram Mini Apps. Например, “freelance SaaS developer” и “custom web application development” — кандидаты для исследования, не подтверждённая частотность или обещание позиций. Для масштабирования поиска предлагаем отдельные содержательные страницы услуг и четыре страницы кейсов при сохранении утверждённой главной.

Региональную адаптацию добавляем, когда конкретный рынок становится приоритетным и есть содержательные отличия: локальный язык, местные запросы, релевантные кейсы, понятные условия сотрудничества и реальные подтверждения присутствия. Пример будущей версии: `de` для немецкоязычной аудитории; `en-GB` — только если делаем отдельное предложение для Великобритании. Название страны само по себе не создаёт полезную посадочную страницу.

Оценка после запуска: запросы и страницы в Search Console с разбивкой по странам; переходы к контактам; фактически полученные обращения и их качество. Общий международный охват не означает одинаковые позиции во всех странах. Приоритеты расширения выбираем по спросу и обращениям.

GEO означает видимость в генеративном поиске. Для Google AI Overviews и AI Mode действуют базовые требования SEO; отдельный обязательный «AI-файл» или специальная разметка не нужны. Подготовим ясные описания услуг, фактические кейсы, роль автора, ответы на вопросы и доступный для индексирования текст. Это повышает понятность содержания, но не гарантирует цитирования. У других ИИ-сервисов проверим собственные правила доступа их поисковых роботов при запуске. Источник: [Google — AI features](https://developers.google.com/search/docs/appearance/ai-features).

## Утверждённый стек

Выбор пользователя от 4 ноября 2026: React + Next.js App Router + TypeScript. Основание — знакомые технологии, готовые маршруты для локалей и кейсов, управление метаданными, возможность постепенно расширять личный сайт. Фреймворк сам по себе не является обещанием поисковых позиций.

| Часть | Решение |
| --- | --- |
| Рендеринг | SSG: главная, услуги и кейсы генерируются заранее в HTML; текст не зависит от запуска игры или клика по карточке |
| Языки | `next-intl`, EN/RU, общие компоненты и отдельный контент локалей |
| Оформление | CSS Modules; существующие цвета, типографика, композиция и адаптивы переносятся без редизайна |
| Интерактивность | Отдельные Client Components для игры и анимаций; игровая логика загружается по необходимости |
| Контент | Файлы Markdown/MDX либо типизированные данные в репозитории; CMS пока не требуется |
| Поисковые настройки | Metadata API, canonical, hreflang, sitemap, robots, Open Graph; структурированные данные только по видимым фактам |
| Контакты | Ссылки Telegram и email; отдельная база данных для текущего сценария не нужна |

Для принятой структуры URL в обычном Next-развёртывании можно использовать `localePrefix: 'as-needed'` и `localeDetection: false`. SSG не равняется обязательному `output: 'export'`: чистый статический экспорт не поддерживает серверный middleware/Proxy, и его маршрутизацию нужно проектировать отдельно. Поэтому окончательный способ развёртывания выбирается вместе с хостингом; не обещаем работу серверной конфигурации на произвольном статическом хостинге.

Кейсы производственной версии получат собственные индексируемые URL. Плавное раскрытие карточки можно сохранить как взаимодействие, при этом прямой переход по ссылке должен открывать полноценную страницу. Основной текст остаётся в готовом HTML. SSR на каждый запрос для редко меняющихся материалов этого лендинга не требуется; новые материалы публикуются при новой сборке.

Nuxt с Vue и предварительным рендерингом остаётся равноценным вариантом для этой задачи. Выбор Next не основан на предположении, что Vue хуже индексируется. Если пользователю удобнее поддерживать Nuxt, менять его ради SEO/GEO не нужно.

Документация: [Next.js — static export](https://nextjs.org/docs/app/guides/static-exports), [Metadata API](https://nextjs.org/docs/app/getting-started/metadata-and-og-images), [локализация](https://nextjs.org/docs/app/guides/internationalization), [next-intl routing](https://next-intl.dev/docs/routing/configuration), [Nuxt — prerendering](https://github.com/nuxt/nuxt/blob/main/docs/1.getting-started/15.prerendering.md).

## Приложение Next.js — первая реализация

Подготовлен отдельный проект stanislav-portfolio-next: App Router, TypeScript, next-intl, CSS Modules. Сохранены исходная палитра, композиция, портрет и SVG-игра; прототип не вставлен в приложение через iframe. Тексты вынесены в EN/RU JSON, факты кейсов — в отдельный файл.

Главные страницы и прямые страницы четырёх кейсов предварительно генерируются при сборке. При переходе к кейсу с главной используется перехватываемый маршрут и диалог; прямой URL открывает самостоятельную страницу. Игровой модуль загружается по нажатию, управление доступно с клавиатуры и телефона.

Подготовлены Metadata API, canonical, языковые альтернативы, sitemap, robots, OG и JSON-LD. До указания реального SITE_URL и ENABLE_INDEXING=true индексация выключена. Эти переменные применяются при сборке. Хостинг должен поддерживать Next.js/Node.js; чистый static export сейчас не используется.

В архив включаются исходники, исходный портрет, package-lock.json, инструкции и проверки. Для запуска достаточно Node.js 24 и команд npm ci / npm run dev. Установка ChatGPT или Codex не нужна. Домен, публикация, подключение Search Console и внешней аналитики остаются следующими действиями после выбора домена.

Проверка реализации: production-сборка и проверка TypeScript проходят; 7 тестов проверяют игровую логику, маршруты локалей и SEO. Smoke-проверки проходят для 10 страниц EN/RU и четырёх ответов 404, а также языкового редиректа, robots, sitemap и OG-изображения. В браузере проверены десктоп, узкие экраны 390/320 px, диалог MedTech, закрытие Escape, переход к контактам, отключение движения, управление игрой и переключение EN/RU на странице кейса. Переключение языка выполняет обычный переход с сохранением кейса, чтобы не активировать перехватываемый диалог другой локали.
